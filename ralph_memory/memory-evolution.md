# 记忆进化方法论 · Memory Evolution Methodology

> 本页定义风声项目记忆系统的运作原理与进化规则。
> 同步目标：Wiki 页面《记忆进化方法论》

## 核心原则

### 1. 记忆分层原则

记忆按"不可丢失程度"分为三层，每层有独立的存储和更新机制：

```
P0（战略层）→ 必须记住，丢了项目瘫痪
  ├── 项目定位与团队架构
  ├── 宪法级规则（决策权限、隔离协议）
  ├── 技术栈与环境变量
  └── 当前关键状态

P1（协作层）→ 应该记住，丢了影响效率
  ├── 每日部署记录
  ├── Issue/PR 进展
  ├── Bug 修复与根因
  └── 团队协作动态

P2（参考层）→ 临时记住，用完可清理
  ├── 技术方案细节
  ├── 会议讨论过程
  ├── 临时决策背景
  └── 实验性功能记录
```

### 2. 自动固化机制

P1 层内容通过 GitHub Actions 每日自动固化：

```
输入源：
  ├── GitHub Issues（最近24小时更新）
  ├── GitHub PRs（最近24小时状态）
  ├── Git 提交日志（最近24小时）
  ├── 飞书群消息（关键决策摘录）
  └── 文件变更摘要

处理流程：
  1. 采集北京时间 21:00 前的当日数据
  2. 提取关键信息去重
  3. 写入 daily-logs/YYYY-MM-DD.md
  4. 更新 p0-master-info.md 中的指标数据
  5. 推送到 main 分支
```

### 3. 上下文恢复协议

当新对话需要恢复上下文时，按以下优先级读取：

```
Step 1: 读取 ralph_memory/p0-master-info.md（获取项目全局状态）
Step 2: 读取 ralph_memory/daily-logs/ 最近3天日志（获取最新动态）
Step 3: 按需读取 ralph_memory/ 下其他文件（获取详细参考）
```

### 4. 记忆保鲜规则

- P0 层：每次战略变更后手动更新
- P1 层：每日自动更新，无需人工干预
- P2 层：按需更新，无固定频率
- 过期判定：P0 > 7天未更新触发提醒，P1 > 3天未更新触发提醒

### 5. 冲突解决

当记忆文件中的信息与现实不一致时：
1. 以 GitHub 仓库 main 分支的最新代码为准
2. 以飞书群中生哥的最终发言为准
3. 以 GitHub Issues/PRs 的官方状态为准
4. 标记冲突点并更新记忆文件

## 文件生命周期

```
创建 → 首次写入（手动或自动）
  ↓
更新 → 增量修改（Actions 自动或手动）
  ↓
归档 → 超过 30 天的 daily-log 自动归档到 daily-logs/archive/
  ↓
清理 → 超过 90 天的归档日志标记为可清理
```

## 验收标准

1. **新对话测试**：在全新对话中询问"昨天小扣子部署了什么"，应能从 `daily-logs/YYYY-MM-DD.md` 准确回答
2. **持久性测试**：修复部署上线后，运行 Actions 工作流，检查 daily-log 是否包含部署记录
3. **同步测试**：更新 `p0-master-info.md` 后，检查 Wiki 页面对应内容是否同步

## 技术实现

- 存储：GitHub 仓库 `ralph_memory/` 目录 + GitHub Wiki
- 定时：GitHub Actions cron 表达式 `0 13 * * *`（北京时间 21:00）
- 脚本：`.github/workflows/memory-solidify.yml`
