> 日期：2026-10-29

> 核心目标：让经纪人在工作台"阶段浏览 → 场景卡 → KB 精选"三跳里，每一跳都能看到有价值的内容，不是空壳

## 一、前端现在怎么用 KB 数据

### 1.1 两个消费场景

| 场景 | 入口 | API | 展示 |
|---|---|---|---|
| **A. 阶段精选面板**（新增） | 工作台 → 切阶段 Tab | `/api/entries?stage=pre&clientType=buyer&limit=10` | Top 5 词条卡：name + consumerQ + cp[0] + sceneDomain + clientType |
| **B. 场景卡底部关联**（已有） | 工作台 → 展开场景卡 | `/api/search/v2?q=公积金贷款&limit=3` | 3 条小链接：name + consumerQ → 点击跳 /entry/ |

### 1.2 展示效果决定因素

前端代码（已上线）直接渲染以下字段：

```
entry.name         → 标题（必填）
entry.consumerQ    → 💡 客户问：xxx
entry.cp[0]        → 核心观点（只取第一条当摘要）
entry.sceneDomain  → 来源标签（如"谈判斡旋"）
entry.tags.clientType → 👤 购房客户/业主/租客
```

## 二、当前内容质量诊断

### 2.1 consumerQ ✅ 合格

```
"听说限购政策要变，对我的房子有什么影响？"     ← 真实口语化
"中介说这个政策出来房价肯定涨，能信吗？"        ← 经纪人能秒懂
"朋友说假离婚能再买一套，有什么风险？"          ← 具体场景
```

### 2.2 cp ❌ 偏干，公式感强

抽样 pre 阶段 6 条 entry 的 cp[0]（前端展示用的那条）：

| cp[0] 示例 | 问题 |
|---|---|
| `限购变→买方资格池变→需求变` | 像逻辑链，不是给经纪人的可执行观点 |
| `确定性价格预测=越界+不可靠` | 偏干，"越界"指什么？经纪人看不懂 |
| `过时政策=信息不可靠→决策失误` | 还行，但没有"怎么办"的指引 |
| `政策分四级：国/省/市/区` | 纯事实，缺行动指向 |
| `利用政策漏洞=规避调控→违法风险` | 还行，但风险具体是什么？ |
| `政策信息官方渠道公开透明` | 太空，"官方渠道"具体是哪？ |

**根因**：cp 最初设计是给"词条详情页"看的 — 5 条堆叠下来是完整的命题论证。但现在前端直接取 cp[0] 当摘要卡展示，就像只给了你一本书的目录第一行，没有结论。

### 2.3 stage 分布不均

| stage | entries 数量 | 来源 |
|---|---|---|
| pre（签约前） | ~1260 条 | 购房准备/了解市场/邀约带看 |
| mid（签约中） | ~1702 条 | 带看议价/交易安全 |
| post（签约后） | ~2539 条 | 过户交接 |

**问题**：pre 阶段是经纪人最常帮客户答疑的阶段，但条目是最少的。而且 OWN-POL（业主政策）类的词条占了 pre 的大头，BUY 侧（购房客户最关心的"贷款/税费/学区/看房"）在 pre 里相对分散。

## 三、具体补全需求（按优先级）

### 🔴 P0 · cp 首条改写（影响 5000+ 条，ROI 最高）

**当前 cp 首条写法**（示例）：
```
cp[0]: "限购变→买方资格池变→需求变"
```

**建议改为**（两种风格任选其一）：

**风格 A · 经纪人话术化**（推荐，直接能用）
```
cp[0]: "政策一变 → 购房资格池跟着变 → 最近想出手的客户得抓紧聊，过两个月价格可能有波动"
```

**风格 B · 行动指引化**
```
cp[0]: "限购政策调整后，购房资格池会收缩或扩张 → 对在售房源挂牌价和成交量有直接影响 → 建议：政策解读后 7 天内是调价窗口期"
```

**改写规则**（给 AI 生产 prompt 用）：
1. cp[0] 必须是**完整的一句话**（主语→行为→后果→建议），不能是公式
2. 必须包含**经纪人视角** — "你应该做什么"而非"事实是什么"
3. 25-60 字之间（前端卡片一行能放下）
4. cp[1-4] 保持原样不变（详情页还是要完整论证）

### 🟡 P1 · consumerQ 补空

当前约有 **15-20% 的词条 consumerQ 缺失** 或太泛（如"什么是学区房"→ 应该是"学区房怎么看对口学校"）。

**补全要求**：
- 每条 entry 至少 1 条 consumerQ
- 分角色补：buyer 侧用客户语气（"我买房需要..."），owner 侧用业主语气（"我卖房能不能..."）
- 一条词条可以有多条 consumerQ（前端 search v2 会用）

### 🟡 P2 · stage 补 BUY 侧密度

当前 pre 阶段（购房准备/了解市场）buyer 侧词条密度不够。经纪人帮**购房客户**答疑高频问题清单（参考 question_map.json 13 条场景卡）：

| 高频场景 | 建议补词条数 | 对应 stage |
|---|---|---|
| 公积金贷款额度/组合贷 | 3-5 条 | pre |
| 首套/二套认定 | 3-5 条 | pre |
| 学区房对口查询 | 3-5 条 | pre |
| 看房注意事项 | 2-3 条 | pre |
| 周边配套评估 | 2-3 条 | pre |

### 🟢 P3 · cp / detail 长度合规

- cp 数组：5 条，每条 20-60 字（当前符合）
- detail：300-800 字（部分 entry 过短 <100 字，部分过长 >1500 字）
- 每条 entry 必须有至少 1 条 `legalRef` 法条依据（当前约 60% 有）

## 四、快速验收清单（前端自测用）

小眼镜补完一轮后，前端可以这样验收：

```bash
# 抽样 pre 阶段 buyer 侧，看 cp[0] 是否改成人话
curl -sS 'https://fengsheng.tech/api/entries?stage=pre&clientType=buyer&limit=10' \
  | python3 -c "
import json,sys
d=json.load(sys.stdin)
for e in d['entries'][:5]:
    print(f'[{e[\"id\"]}] {e[\"name\"][:40]}')
    cp0 = e.get('cp',[''])[0]
    if '→' in cp0 or '=' in cp0:
        print(f'  ⚠️ 仍是公式: {cp0[:60]}')
    else:
        print(f'  ✅ 人话: {cp0[:60]}')
    print(f'  consumerQ: {e.get(\"consumerQ\",\"\")[:50]}')
"
```

验收通过标准：抽样 10 条，**≥7 条 cp[0] 是完整句子**（不含 `→` 和 `=` 作为主要结构符）。
