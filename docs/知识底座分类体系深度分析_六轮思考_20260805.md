# 知识底座分类体系深度分析 — 六轮思考

> 日期：2026.8.5
> 起因：生哥质疑"为啥只加2个域？10个域是否穷尽？数据字典属于哪类？怎么搭建更全面深入的数据支撑？"
> 方法：六轮逐层深入，每轮推翻上一轮的结论

---

## 第一轮：当前8域到底有什么问题？

### 表面问题：命名混乱

当前domain字段实际有32个不同的值，分4种命名体系混在一起：

| 命名体系 | domain值 | 条数 |
|----------|----------|------|
| 中文阶段名 | 签约前/签约中/签约后/居住中/退租出售 | 2786 |
| 中文功能名 | 资产持有与运营/职业成长/业主/跨域通用 | 1497 |
| 英文代码 | trade/SNG/OWN/CAR | 1050 |
| 字母编码 | A1-A4/B1-B4/C1-C3/G1-G4/H1-H4 | 155 |

这不是"8个域"，是**4种不同分类维度塞进同一个字段**。

### 深层问题：维度混淆

| 维度 | 含义 | 当前被塞进domain的例子 |
|------|------|----------------------|
| 时间阶段 | 什么时候发生？ | 签约前/中/后、居住中、退租出售 |
| 业务功能 | 做什么事？ | 资产运营、trade(谈判)、SNG(资金税务)、CAR(合规) |
| 角色视角 | 谁的视角？ | 业主、OWN |
| 知识主题 | 关于什么？ | A1(不动产法律)、C1(学区政策)、G(装修)、H(资产管理) |
| 元知识 | 关于知识本身 | 职业成长、跨域通用 |

**核心问题：domain字段在做4份不同的工作，导致它哪份都没做好。**

## 第二轮：居住服务者到底需要什么知识？

抛开现有domain，从零开始想：一个居住服务者服务客户全流程需要什么知识？

### 经纪人的一天

```
早上：发朋友圈/回复客户消息 → 获客与客户管理
上午：带看3套房 → 房源与匹配 + 带看与展示
中午：跟业主谈价格 → 谈判与撮合
下午：帮客户算首付税费 → 资金与税务
傍晚：拟合同走网签 → 签约与合规
晚上：处理租客投诉漏水 → 纠纷与维权 + 居住服务
```

### 14个业务能力域

| 编号 | 能力域 | 经纪人要做什么 | 当前条数 | 覆盖率 |
|------|--------|--------------|---------|--------|
| D1 | 获客与客户管理 | 找客户、建信任、摸需求、管关系 | 267 | ⚠️ 获客本身几乎为0 |

| D6 | 资金与税务 | 贷款、税费计算、资金监管、保险 | 716 | ✅ 充分 |
| D7 | 交房与售后 | 验房、交房、售后服务 | 149 | ⚠️ 偏薄 |

### MECE检验

- D1(获客) vs D12(心理沟通)：获客是"找到人"，心理沟通是"理解人" → ✅不重叠
- D4(谈判) vs D5(签约)：谈判是"达成共识"，签约是"法律执行" → ✅不重叠
- D7(交房) vs D8(资产运营)：交房是"一次性交付"，运营是"持续管理" → ✅不重叠
- D11(市场洞察) vs D14(特殊场景)：市场是"宏观环境"，特殊场景是"特定品类" → ✅不重叠
- D13(职业成长) vs D5(合规)：职业成长是"经纪人自己的事"，合规是"业务操作规范" → ✅不重叠

**结论：14个能力域基本MECE。当前最大缺口在D1获客(≈0条)、D3带看(40条)、D12心理沟通(75条)。**

## 第三轮：14个域够不够？有没有遗漏？

### 逐个排查遗漏

**遗漏1：品牌营销与个人IP**
经纪人需要做自媒体、发朋友圈、建个人品牌。当前：13条（品牌营销关键词命中）。
→ 这应该独立成域吗？还是归入D1获客？
→ **结论：归入D1获客与客户管理**，因为个人品牌的本质是获客手段。

**遗漏2：数字化工具与AI应用**
经纪人需要用系统、工具、AI提效。当前：28条。
→ 这应该独立成域吗？
→ **结论：归入D13职业素养与成长**，因为工具使用是职业技能的一部分。

**遗漏3：团队管理**
店长/团队长需要管人、管绩效。当前：286条。
→ 这应该独立成域吗？
→ **结论：独立成D15团队管理与门店运营**。因为这是管理者的知识，不是个人经纪人的知识，用户群体不同。

**遗漏4：服务品质与客户体验**
服务标准化、客户满意度、口碑管理。当前：4条。
→ 这应该独立成域吗？
→ **结论：归入D1获客与客户管理**。因为服务品质的核心目的是留存和转介绍，本质是获客的延续。

**遗漏5：政策法规总览**
A1-A4、C1-C3这些是按知识主题分的，不是按业务能力分的。
→ 不动产法律 → 归入D5签约与合规
→ 调控政策 → 归入D11市场洞察与趋势
→ 税费法规 → 归入D6资金与税务
→ 学区政策 → 归入D14特殊场景与人群
→ **结论：不需要独立的"政策法规"域，政策法规是每个域的entryType=POL子集。**

## 第四轮：数据字典属于哪类？

### 数据字典的本质

当前数据字典76条×9场景，内容是：
- 各城市首付比例
- 各城市限购政策要点
- 各城市税费速算标准
- 各城市公积金贷款额度
- 等等

这些不是"知识"（教你怎么做），而是"数据"（给你具体数字）。

### 三层架构

知识底座应该有三层，不是一层：

```
┌─────────────────────────────────────┐
│  知识层 (Knowledge Layer)            │  ← 5417条词条
│  回答：是什么？怎么做？有什么风险？   │
│  字段：detail, ola, cp, legalRef     │
├─────────────────────────────────────┤
│  数据层 (Data Layer)                 │  ← 数据字典76条 + 待建
│  回答：具体数字是多少？标准是什么？   │
│  字段：dataRef (当前99.7%为空)       │
├─────────────────────────────────────┤
│  案例层 (Case Layer)                 │  ← 待建
│  回答：有没有真实判例？行业怎么做的？ │
│  字段：caseRef (当前100%为空)        │
└─────────────────────────────────────┘
```

### 数据字典的定位

数据字典 = **数据层的索引**，不是知识层的一个domain。

它应该：
1. 独立于知识层存在，有自己的schema（场景→数据项→数据值→来源→更新时间）
2. 通过dataRef字段被知识层引用
3. 按场景组织（当前9场景），不按domain组织
4. 支持多城市、多时间点的数据（当前只有部分城市）

### 当前问题

- dataRef字段100%填充但99.7%是"待补充数据" → **假填充**
- caseRef字段100%填充但100%是"待补充案例" → **假填充**
- 数据字典76条只是骨架，没有与5417条词条建立引用关系
- 没有数据更新机制（利率/税率/政策会变）

### 修复方案

1. **dataRef改为引用数据字典ID**：`dataRef: "DD-LOAN-001"` 而非 `dataRef: "待补充数据"`
2. **数据字典扩展**：从76条扩展到200+条，覆盖15个能力域的核心数据需求
3. **caseRef改为引用案例库ID**：`caseRef: "CASE-001"` 而非 `caseRef: "待补充案例"`
4. **案例库建设**：从法院判例、行业案例中提取，与词条关联

## 第五轮：怎么搭建更全面深入的数据支撑？

### 当前数据支撑现状

| 维度 | 现状 | 问题 |
|------|------|------|
| 知识广度 | 5417条×15域 | D1获客/D3带看/D12心理沟通严重缺口 |
| 知识深度 | 道法术器4层 | 分布不均，器层多在CAR/SNG |
| 数据引用 | dataRef 0.3%真实 | 几乎没有真实数据支撑 |
| 案例佐证 | caseRef 0%真实 | 完全没有案例佐证 |
| 业主视角 | ownerQ 38.5% | 超过6成词条没有业主视角 |
| 避坑提示 | caveat 35.7% | 近7成词条没有避坑提示 |
| 工具类型 | toolType 10.1% | 9成词条没有工具卡分类 |

### 深度数据支撑的五个层次

**层次1：知识广度补齐**
- D1获客：从0→100条（拓客方法、客户画像、关系维护、个人品牌）
- D3带看：从40→120条（看房流程、亮点话术、异议处理、动线设计）
- D12心理：从75→150条（客户心理、信任建立、话术模板、异议应对）
- 合计需新增~235条

**层次2：数据层建设**
- 数据字典从76条→300条（覆盖15域×20条核心数据）
- 每条数据字典含：数据项名、数据值、适用城市、来源、发布日期、更新频率
- dataRef从0.3%→60%+（核心词条必须引用真实数据）
- 数据来源：央行/住建部/税务局/各地公积金中心/中指研究院

**层次3：案例层建设**
- 案例库从0→500条（法院判例300+行业案例200）
- 每条案例含：案例编号、案情摘要、裁判结果、适用法条、关联词条、时间
- caseRef从0%→40%+（LAW/RISK/CASE类型必须引用真实案例）
- 来源：中国裁判文书网、各地法院公报、行业协会案例库

**层次4：视角补全**
- ownerQ从38.5%→80%+（有业主场景的词条必须有业主视角）
- ownerBenefit从22.6%→80%+（有ownerQ的词条必须有ownerBenefit）
- caveat从35.7%→70%+（RISK/LAW/PROC类型必须有caveat）
- toolType从10.1%→50%+（核心词条必须有工具卡分类）

**层次5：动态更新机制**
- 政策类词条：每季度核查（已建立巡采系统）
- 数据类词条：利率/税率/标准每年更新
- 案例类词条：每月新增5-10条最新判例
- 知识反哺：4条巡采线持续捕获变化（已建立）

### 建设优先级

| 优先级 | 任务 | 工作量 | 预期效果 |
|--------|------|--------|---------|
| P0 | dataRef真实化（核心200条） | 2天 | 知识有数据支撑 |
| P0 | caseRef真实化（LAW/RISK 300条） | 3天 | 知识有案例佐证 |
| P1 | caveat全量补扫（1656条） | 1天 | 避坑提示全覆盖 |
| P1 | ownerBenefit batch2（863条） | 0.5天 | 业主视角补全 |
| P2 | D1/D3/D12词条补产（235条） | 3天 | 业务覆盖无死角 |
| P2 | ownerCard补扫（941条） | 1天 | 业主卡片全覆盖 |
| P3 | toolType全量分类（4870条） | 2天 | 工具卡体系化 |
| P3 | 数据字典扩展（76→300条） | 3天 | 数据层完善 |
| P3 | 案例库建设（500条） | 5天 | 案例层建立 |

## 第六轮：最终架构建议

### 多维分类模型

不要试图用单一domain字段解决所有分类问题。应该是：

```
每条词条 = {
  // 维度1：业务能力域（新增 tags.capability）
  capability: "D5-签约与合规",      // 15个能力域之一
  
  // 维度2：服务阶段（保留 tags.stage）
  stage: "mid",                      // pre/mid/post/all
  
  // 维度3：知识类型（保留 entryType）
  entryType: "LAW",                  // LAW/PROC/CASE/RISK/STD/POL/TERM
  
  // 维度4：认知层次（保留 tags.layer）
  layer: "fa",                       // dao/fa/shu/qi
  
  // 维度5：客户视角（保留 clientType，需补全）
  clientType: ["buyer", "landlord"], // buyer/tenant/seller/landlord/owner/agent
  
  // 维度6：见面阶段（保留 tags.meetingPhase）
  meetingPhase: ["见前", "见中"],     // 见前/见中/见后
  
  // 内容字段
  name, detail, ola, cp, legalRef,  // 知识内容
  dataRef, caseRef,                  // 数据和案例引用
  ownerQ, ownerBenefit, ownerCard,   // 业主视角
  caveat, toolType,                  // 避坑提示和工具类型
}
```

### 旧domain字段处理

| 旧domain | 映射到 capability | 说明 |
|----------|------------------|------|
| 签约前 | D1/D2/D3/D4/D6 (按subScene拆) | 签约前包含获客/匹配/带看/谈判/资金 |
| 签约中 | D5-签约与合规 | 直接映射 |
| 签约后 | D7-交房与售后 | 直接映射 |
| 居住中 | D8-资产运营 / D10-纠纷维权 | 按subScene拆 |
| 资产持有与运营 | D8-资产运营与管理 | 直接映射 |
| 退租出售 | D9-退出与再交易 | 直接映射 |
| 业主 | 按subScene拆到D7-D10 | 业主不是能力域，是clientType |
| OWN | 按subScene拆到D7-D10 | 同上 |
| 职业成长 | D13-职业素养与成长 / D15-团队管理 | 按subScene拆 |
| trade | D3/D4/D12 (按subScene拆) | 客户解码→D12, 谈判→D4, 带看→D3 |
| SNG | D6-资金与税务 | 直接映射 |
| CAR | D5-签约与合规 | 直接映射 |
| A1 | D5-签约与合规 | 不动产法律→合规 |
| A2 | D11-市场洞察与趋势 | 调控政策→市场 |
| A3 | D6-资金与税务 | 税费法规→资金税务 |
| A4 | D8-资产运营与管理 | 租期内服务→运营 |
| C1-C3 | D14-特殊场景与人群 | 学区→特殊场景 |
| G1-G4 | D8-资产运营与管理 | 装修→运营 |

### 三层架构

```
┌──────────────────────────────────────────────┐
│  应用层（小豆子端）                            │
│  小程序/网页/API → 按场景调用知识              │
├──────────────────────────────────────────────┤
│  知识层（5417条 → 5652条）                     │
│  15个能力域 × 4层 × 8种类型                    │
│  每条含：内容 + 业主视角 + 避坑提示 + 工具类型  │
├──────────────────────────────────────────────┤
│  数据层（300条数据字典）                        │
│  15域 × 20条核心数据 × 多城市                  │
│  通过dataRef被知识层引用                       │
├──────────────────────────────────────────────┤
│  案例层（500条真实案例）                        │
│  法院判例300 + 行业案例200                     │
│  通过caseRef被知识层引用                       │
└──────────────────────────────────────────────┘
```
