## 一、产品定位与核心理念

**一句话定位**：居住服务者的专业基础设施。

**官网 slogan**：把效率交给工具，把**专业**留给你。

**核心主张**：知识底座 + 数字工具，帮居住服务者把查证、检索、写方案这类"效率活"干完，让服务者腾出手做更重要的判断与担当。

**价值公式**：美好居住 = 物质得到保障 + 情感得到满足 + 精神得到尊重。

### 五大核心支柱（品牌理念 → 产品）
知识底座页用「四柱撑起美好居住」的比喻，把品牌哲学落到产品结构：

| 支柱 | 精神内核 | 对产品的隐喻 |
|------|---------|-------------|
| 🌱 文化 | 损有余而补不足 | 帮信息差弱者补齐认知，不为客户做嫁衣 |
| 🎯 使命 | 帮服务者贴近消费者认知 | 知识底座 ≠ 决策工具 |
| 🔭 愿景 | 人人美好居住 | 放大人不替代人 |
| ⚖️ 价值观 | 长而不宰 | 让人觉得自主决定，方向恰好对 |

**产品启发**：品牌理念不是装饰，而是产品边界——一切功能都从这四个支柱长出来，保持"帮服务者"而非"替代服务者"的克制。

统一在 `index.html` 的 CSS `:root` 变量里，方便全站复用、长期维护。


## 三、信息架构与导航逻辑

### 3.1 首页导航策略
首页不是"一堆功能入口"而是"价值先导 + 角色分流"：

```
先价值（定位一句话）
  → 三角色切换（经纪人 / 管理者 / 新用户）
    → 每角色各自：场景卡片（拿来即用）+ 工具箱（全部工具）
  → 今日知识（每日一词条，培养习惯）
  → 风声AI助手（右下角悬浮，随时随地提问）
```

| 角色 | 功能 | 路径 |

## 四、角色体系：先选角色再看方案

这是风向最值得借鉴的交互：**同一套内容，按角色重排信息架构**。

```js
// 三角色切换
switchRole('agent')    // 经纪人：带法源知识库，生成客户沟通方案
switchRole('manager')  // 管理者：搭建团队数字员工，量化服务质量
switchRole('newbie')   // 新用户：花3分钟，看我能提成的价值
```

每个角色对应一套独立的 **场景卡片 + 工具箱**，用户"先认领身份，再看到对自己有用的东西"，大幅降低新用户的理解成本。

- 经纪人：遇到买房客户 → 策展引擎；想提升 → 知识库/测评；要回复问题 → AI对话；管理客户 → 客户档案。
- 管理者：运营看板 / 数字员工看板 / 五把尺子考核 / 智慧体学院 / 方法论工具包。
- 新用户：三步走引导（完成测评 → 浏览知识库 → 尝试策展引擎）+ 进度追踪，构成轻量 onboarding。

## 五、页面模块全景

### 5.1 知识库 `/knowledge/`
「学」板块的核心，承载品牌理念 + 知识基本面：
- 顶部四支柱理念展示
- 数据概览（词条数、业务域、岗位、能力点）
- 全局搜索框 + 推荐搜索词
- **知识掌握度测评入口卡片**
- 业务域分类浏览

### 5.2 词典 `/dictionary/`
词条总览，支持按 7 维筛选（clientType 客户类型 / stage 阶段 / layer 层级 / domain 业务域 / entryType / severity / priority），检索 + 筛选双通道。

### 5.3 策展引擎 `/curation/`
面向经纪人的「客户全生命周期报告生成器」——把知识库 + 数据字典组合成一份可交付客户报告，是"知识 → 业务应用"的落地样板。

### 5.4 品质测评 `/care-test/` 与 五把尺子 `/assessment/`
- 品质测评：服务者个人专业水平自测。
- 五把尺子：管理者用于绩效评分（工作量 / 复杂度 / 复用 / 运行 / 并发）。

### 5.5 智能体学院 `/agent-academy/`
管理者"训练数字员工"的方法论，含岗位职责模板、协作方法论、成功案例、落地辅导（加微信预约）。

### 5.6 运营看板 `/dashboard/`、数字员工看板 `/dashboard-manager/`
前者对主站 / 小程序 / 转化 / 健康监控；后者对团队数字员工（岗位分布 / 产出 / 评分排名）。

### 5.7 方法论工具包 `/toolkit/`
可下载 / 可打印的完整方法论报告，积累可复用资产。

## 七、掌握度测评：「考」的落地

### 7.1 定位
「按业务模块 × 场景」检测用户对知识底座的掌握度，错题可反查词条温习——把"考"与"学"闭环打通。

### 7.2 目录式页面机制（重点借鉴）
```
knowledge/
├── index.html      # 知识库首页（含测评入口卡片）
├── quiz-data.js    # 测评题库数据（window.KNOWLEDGE_QUIZ）
└── quiz/
    └── index.html  # 测评页面（目录式，可被 /knowledge/quiz/ 访问）
```

**特殊处理**：`/knowledge/quiz/` 是**二级目录页面**，必须同时满足：
1. 目录式结构存放 `index.html`；
2. `_redirects` 加兜底规则 `/knowledge/quiz /knowledge/quiz/ 200`（兼容无尾斜杠）；
3. **最关键**——真正导致 404 的坑是 `_worker.js` 里的 `KNOWN_ROUTES` 白名单，必须把 `/knowledge/quiz` 加进去，否则会被 Worker 强制 404 掉（即使文件存在）。

### 7.3 测评交互逻辑
```js
var QUIZ = window.KNOWLEDGE_QUIZ || [];
var state = { moduleIdx:-1, sceneIdx:-1, qs:[], cur:0, picks:{}, answered:0 };
```
流程：**选模块 → 选场景 → 答题（判断/选择）→ 即时正误反馈 + 解析 → 结果(正确率+等级+错题清单) → 错题可温习词条**。

- 题型：判断题（对/错）、选择题（四选一）。
- 每题带 `explanation`（解析）与 `entry`（关联词条），答完即展示正误与解析。
- 结果页按正确率评定等级：≥90 掌握优秀 / ≥70 基本掌握 / ≥50 有待加强 / <50 需要重学，并汇总错题清单供温习。

## 八、数据资产与字段设计

数据全部以 JSON 落地，按"领域建模"而非"表格堆砌"，便于长期扩展与跨端复用。

### 8.1 知识词条 entries.json（5843 条）
```json

  "id": "CAR-CMP-CASE-001",
  "domain": "CAR",
  "sceneDomain": "职业成长",
  "subScene": "合规",
  "name": "承诺包过户没办成中介要赔违约金吗",
  "alias": ["中介承诺包过户没办成怎么办", "..."],
  "legalRef": "《中华人民共和国民法典》第五百七十七条",
  "consumerQ": "中介说包过户但最后没办成，我能要求退钱吗？",
  "consumerBenefit": "明确中介承诺的法律效力，保障自身交易权益。",
  "severity": "hard",
  "lastVerified": "2026-07-27",
  "relatedEntries": ["CAR-COMP-023", "..."],
  "source": "司法判例",
  "entryType": "CASE",
  "priority": "P0",
  "dataSource": "《民法典》第五百七十七条及某市法院2022年民事判决书",
  "tags": {"clientType":["agent"], "stage":"mid", "layer":"qi", "meetingPhase":["见中","见前"]},
  "detail": "...完整案情...",
  "ola": "中介在微信中承诺包过户构成合同义务，未尽购房资格核查致无法过户，判退全额佣金并赔2万元",  // 一句话结论
  "cp": ["口头承诺具有法律效力", "微信记录可作为证据", "未核查资格需担责", "违约需退还佣金并赔偿"],  // 要点
  "caseRef": "待补充案例",
  "toolType": "风险卡"

```

**字段设计要点**：
- `consumerQ`：客户怎么问（一句人话）→ 知识呈现入口。
- `ola`：一句话大白话结论 → 用户先看懂，再决定要不要深读。
- `cp`：要点数组 → 可二次加工为判断题 / 摘要。
- `legalRef` / `dataSource`：法条可溯源 → 专业可信。
- `relatedEntries`：词条间关联 → 支撑"相关推荐 / 思维导图"。
- `tags`：多维标签（用户类型/阶段/层级/见面环节）→ 支撑筛选与场景化组织。

### 8.5 工具卡 broker_toolkit.json / 数据字典 data_dictionary_v2.0.json

## 九、技术架构与部署

### 9.1 技术栈
| 层 | 选型 |
|----|------|
| 前端 | 原生 HTML/CSS/JS（Jinja2 变体/纯静态） |
| 宿主 | Cloudflare Pages（静态站点） |
| 边缘运行时 | `_worker.js`（Cloudflare Worker，负责路由 / API / SPA fallback） |
| 数据 | 本地 JSON + KV 缓存（`env.CACHE`） |
| CI/CD | GitHub Actions → `cloudflare/wrangler-action@v3` |

### 9.2 三个关键配置文件

**`_worker.js`（核心路由）**
- 拦截所有请求，暴露 REST 型 API：`/api/entries`、`/api/entry`、`/api/dictionary`、`/api/search`、`/api/search/suggest`、`/api/scene/*`、`/api/favorites`、`/api/history`、`/api/heartbeat`、`/api/chats` 等。
- **目录页白名单 `KNOWN_ROUTES`**：对无文件扩展名的 HTML 路径强制白名单校验，未登记直接 404（防 SPA 全量 fallback）。**新增目录页必须加白名单**，否则 404。
- API 统一兜底：未匹配的 `/api/*` 返回 JSON 404，正常路由遇到 404 返回定制 404 页。

**`_redirects`（路由兜底）**
- 目录式页面的无尾斜杠兼容：`/knowledge/quiz /knowledge/quiz/ 200`。
- 历史迁移：如 `/knowledge.html → /knowledge/ 301`。

**`_headers`（安全加固）**
- 全局 CSP / HSTS / X-Content-Type-Options / X-Frame-Options / Referrer-Policy / Permissions-Policy。
- HTML 走 `must-revalidate`；静态资源走缓存策略。

### 9.3 目录式页面规则（解决 404 的关键，务必遵守）
1. 新页面一律放 `xxx/index.html`，不用 `xxx.html`。
2. `_redirects` 加 `200` 兜底兼容无尾斜杠。
3. **`_worker.js` 的 `KNOWN_ROUTES` 加白名单**（二级目录尤其容易漏）。
4. 推送 main 分支 → GitHub Action 自动 `pages deploy ./ --project-name=fengsheng --branch=main` 到 `fengsheng.tech`。

## 十、关键交互设计

### 10.1 风声AI助手
右下角悬浮 FAB，会话型交互。前端 `fetch` 流式渲染 Coze 原生 SSE（`/mentor-api/chat`），逐字输出，带给用户"实时对话"的体验。

### 10.2 今日知识
每日从知识底座精选一条词条，按 `clientType`（买方/业主/租户）+ `stage`（售前/售中）配场景，养成"每天学一点"的习惯，也是知识库的常温触达。

### 10.3 新用户三步引导
测评 → 知识库 → 策展引擎，带进度条（●○○○○），把 onboarding 变得可玩、可追踪。

## 十一、给开发者的最佳实践与借鉴点

1. **价值先导，角色分流**：不要把页面做成"功能堆砌"，先让用户认领身份，再按身份展示对其有用的内容。
2. **品牌理念 = 产品边界**：万物从知识底座长出，克制地"帮服务者而非替代者"。
3. **目录式页面 + 三层兜底**：index.html / `_redirects` / `_worker.js` 白名单，三者缺一不可（血的教训：漏白名单 → 静默 404）。
4. **数据一次建模，多端复用**：一份 entry 兼具"词典条目、判断题源、案例关联、风险卡素材"，靠 `relatedEntries` + `sceneDomain` 做场景聚合。
5. **同一套筛选维度贯穿**：clientType/stage/layer/severity/priority 等 tag 既是知识库筛选，也是测评、案例、工具的组织维度。
6. **可溯源专业内容**：每条词条带 `legalRef/dataSource/lastVerified`，长期可用、可信可查。
