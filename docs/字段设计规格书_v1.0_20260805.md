## 一、为什么有这份文档

生哥质疑：**字段凭什么是这些？从经纪人视角够不够？**

事实纠正：当前不是21个字段，是**35个**（22核心+5部分填充+8实验字段）。但字段从9→25→35的演进过程中，确实缺一份系统性的设计规格书。这份文档补上这个缺口。

---

## 二、设计原则

### 2.1 三条铁律

| 原则 | 含义 | 验证标准 |
|------|------|----------|
| **知识管理者可维护** | 每个字段有明确的填充规则和校验逻辑 | quality_checker.py 能自动校验 |
| **经纪人可直接用** | 字段内容能直接转化为经纪人的话术、动作或判断依据 | 拿到一条词条，经纪人30秒内知道"对客户怎么说" |
| **引擎可调度** | 字段能被小豆子引擎按场景调取和组合 | tags三维+sceneDomain+entryType 能精确定位 |

### 2.2 字段分层逻辑

```
┌─────────────────────────────────────────────────────┐
│  核心层（22字段·100%填充）                           │
│  每条词条必须有，缺一不可                            │
│  → 定位 + 内容 + 依据 + 受众 + 标签                  │
├─────────────────────────────────────────────────────┤
│  扩展层（5字段·部分填充）                             │
│  按条件填充，不是每条都有                            │
│  → 业主视角 + 风险提示 + 工具类型                    │
├─────────────────────────────────────────────────────┤
│  实验层（8字段·<1%填充）                             │
│  FDE深度词条专用，尚在验证                          │
│  → 话术模板 + 正反话术 + 场景锚定 + FDE链路          │
└─────────────────────────────────────────────────────┘
```

## 三、核心层字段（22个·100%填充）

### 3.1 定位字段（4个）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 1 | `id` | string | 全局唯一标识，格式`{DOMAIN}-{SCENE}-{TYPE}-{SEQ}` | `BUY-LOAN-PROC-001` |
| 2 | `domain` | string | 知识域（8域之一） | `金融贷款` |
| 3 | `sceneDomain` | string | 场景域（业务线+视角） | `金融贷款·买方侧` |
| 4 | `subScene` | string | 子场景（32子域之一） | `商贷` |

**设计依据**：三层定位 = 域→场景域→子场景，确保每条词条在知识分类体系中有唯一坐标。对应全域重构v1.0的8域×32子域结构。

### 3.2 内容字段（5个）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 5 | `name` | string | 词条标题（问句式，口语化） | `公积金贷款额度怎么算` |
| 6 | `alias` | string[] | 搜索别名（每条5-7个，覆盖口语问法） | `["公积金能贷多少","公积金贷款上限",...]` |
| 7 | `detail` | string | 详细解答（200-500字，经纪人可直接读给客户） | 完整解答文本 |
| 8 | `ola` | string | One-Line Answer 一句话答（30字以内，电梯话术） | `按账户余额的15倍计算，最高120万` |
| 9 | `cp` | string[] | Core Points 核心要点（3-6条， bullet形式） | `["按余额15倍计算","最高120万","..." ]` |

**设计依据**：三层信息密度 = 详答(detail) > 要点(cp) > 一句话(ola)。经纪人根据场景选择信息密度——电梯里用ola，面谈用cp，深度咨询用detail。alias确保口语搜索命中率。

### 3.3 依据字段（4个）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 10 | `legalRef` | string | 法律依据（法条名+条文号） | `《住房公积金管理条例》第26条` |
| 11 | `dataRef` | string | 数据支撑（引用数据字典条目） | `DATA-LOAN-001:杭州公积金最高额度` |
| 12 | `caseRef` | string | 案例佐证（引用案例库条目） | `CASE-LOAN-003:公积金贷款被拒案例` |
| 13 | `source` | string | 信息来源（标注出处） | `法律条文+行业惯例` |

**设计依据**：每个知识单元挂三个维度 = 法律依据(legalRef) + 数据支撑(dataRef) + 案例佐证(caseRef)。这是知识底座的核心质量标准——**有依据才叫知识，没依据叫观点**。legalRef已100%覆盖且经过法条真实性验证。

### 3.4 受众字段（4个）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 14 | `consumerQ` | string | 客户视角问法（客户会怎么问） | `公积金能贷多少？` |
| 15 | `consumerBenefit` | string | 客户收益（客户为什么要知道） | `提前规划购房预算，避免看房后才发现额度不够` |
| 16 | `entryType` | string | 词条类型（8类） | `LAW/PROC/CASE/RISK/STD/POL/TERM/Knowledge` |
| 17 | `priority` | string | 优先级 | `P0/P1/P2` |

**设计依据**：consumerQ和consumerBenefit强制从客户视角设计——**不是"经纪人要背什么"，而是"客户会问什么、客户得到什么"**。entryType区分知识性质，priority指导上线节奏。

### 3.5 标签字段（1个·三维四标）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 18 | `tags` | object | 三维标签 | 见下 |

```json
{
  "clientType": ["buyer", "landlord"],   // 谁用
  "stage": "pre",                         // 什么阶段(pre/mid/post/all)
  "layer": "fa",                          // 道法术器(dao/fa/shu/qi)
  "meetingPhase": ["见前", "见中", "见后"] // 见客户阶段
}
```

**设计依据**：三维标签是引擎调度的核心索引。clientType决定"给谁看"，stage决定"什么时候用"，layer决定"什么深度"，meetingPhase决定"见面哪个环节用"。已100%覆盖5417条且全部规范化。

### 3.6 元数据字段（4个）

| # | 字段 | 类型 | 说明 | 示例 |
|---|------|------|------|------|
| 19 | `severity` | string | 难度等级 | `easy/medium/hard` |
| 20 | `lastVerified` | string | 最后验证日期 | `2026-07-29` |
| 21 | `relatedEntries` | string[] | 关联词条ID列表 | `["BUY-LOAN-001", "BUY-LOAN-002"]` |
| 22 | `dataSource` | string | 数据来源标注 | `《民法典》第九百六十六条` |

**设计依据**：severity帮经纪人判断"这个问题好不好答"；lastVerified确保知识时效性（政策类每季度核查）；relatedEntries构建知识网络，支持"相关问题推荐"。

## 四、扩展层字段（5个·条件填充）

### 4.1 业主视角字段（3个）

| # | 字段 | 填充率 | 填充条件 | 说明 |
|---|------|--------|----------|------|
| 23 | `ownerQ` | 38.5% | OWN域词条必填 | 业主视角问法 |
| 24 | `ownerBenefit` | 3.0% | OWN域词条必填 | 业主收益 |
| 25 | `ownerCard` | 21.1% | OWN域词条必填 | 业主工具卡（title+oneLineAnswer+ownerBenefit） |

**当前问题**：ownerQ和ownerBenefit填充率远低于OWN域词条总数。ownerBenefit仅3.0%是硬伤——**OWN域词条必须带ownerQ和ownerBenefit字段**（MEMORY.md已写入此规则），但实际执行不到位。

**修复方案**：对OWN域词条做一次全量补扫，确保ownerQ/ownerBenefit/ownerCard 100%覆盖。

### 4.2 风险提示字段（1个）

| # | 字段 | 填充率 | 填充条件 | 说明 |
|---|------|--------|----------|------|
| 26 | `caveat` | 35.7% | 涉法/涉风险词条应填 | 反证位/注意事项/红线提醒 |

**设计依据**：六顶思考帽黑帽提出的"caveat反证位"概念。每条涉法词条应标注"什么情况不适用""有什么例外""不能做什么"。当前35.7%偏低，理想目标是涉法词条(RISK/LAW/PROC类型)100%覆盖。

### 4.3 工具类型字段（1个）

| # | 字段 | 填充率 | 填充条件 | 说明 |
|---|------|--------|----------|------|
| 27 | `toolType` | 10.1% | 器层(qi)词条应填 | 工具卡片类型（决策卡/对比表/流程图/话术卡/清单卡） |

**当前问题**：仅547条有toolType，但器层词条远不止这个数。需要按layer=qi条件全量补扫。

这8个字段来自FDE(Framework-Driven Entry)深度词条实验，仅在47条OWN-SEL-DEEP系列词条中填充。

| # | 字段 | 填充率 | 说明 | 是否建议转正 |
|---|------|--------|------|-------------|
| 28 | `depth` | 0.9% | 深度标记（deep/standard/quick） | ⚠️ 建议废弃，用priority替代 |
| 29 | `brokerNote` | 0.9% | 经纪人内部备注（怎么操作） | ✅ 建议转正→见第六节 |
| 30 | `posSpeech` | 0.9% | 正向话术（professional+empathy两版） | ✅ 建议转正→见第六节 |
| 31 | `negSpeech` | 0.9% | 反向话术（warning+redline两版） | ✅ 建议转正→见第六节 |
| 32 | `caseIds` | 0.9% | 关联案例ID列表 | ⚠️ 与caseRef重复，建议合并 |
| 33 | `lawLayer` | 0.9% | 法律层级（法律规律/法律规则/法律原则） | ⚠️ 建议废弃，与legalRef冗余 |
| 34 | `sceneId` | 0.9% | 场景锚定ID | ⚠️ 与subScene+tags冗余 |

- **转正3个**：brokerNote / posSpeech / negSpeech → 合并为第六节的2个新字段

- **合并1个**：caseIds → 并入caseRef

## 六、建议新增字段（5个）

基于六顶思考帽分析（黑帽5硬伤+绿帽创新提案），建议新增以下5个字段：

### 6.1 `brokerScript` — 经纪人话术模板

| 属性 | 值 |
|------|-----|
| 类型 | object |
| 填充条件 | P0词条应填，P1选填 |
| 来源 | 合并实验字段 brokerNote + posSpeech + negSpeech |

```json
{
  "brokerScript": {
    "note": "告诉业主：独家委托到期后自动终止，中介无权强制续签。",
    "positive": {
      "professional": "姐，您这份独家委托7月15号就到期了，到期后您有权随时更换中介。",
      "empathy": "我理解您担心得罪中介，但独家委托是您给中介的特权，到期了自然收回。"
    },
    "negative": {
      "warning": "不要签含自动续约条款的独家协议，这类条款可能被认定为格式条款无效。",
      "redline": "不能威胁中介说不给解约就投诉——要依法依约办事。"
    }
  }
}
```

**设计依据**：六顶思考帽黑帽第1硬伤——缺"怎么说"话术类字段。当前brokerNote/posSpeech/negSpeech散落在3个实验字段中，合并为1个结构化字段，经纪人拿到就知道"专业版怎么说、共情版怎么说、什么不能说"。

### 6.2 `objectionHandler` — 客户反问应对

| 属性 | 值 |
|------|-----|
| 类型 | array[{q, a}] |
| 填充条件 | P0词条应填，高频异议场景必填 |

```json
{
  "objectionHandler": [
    {
      "q": "中介说解约要赔违约金怎么办？",
      "a": "独家委托到期后自动终止，合同中约定的违约金条款仅适用于委托期内。到期后不存在违约。"
    },
    {
      "q": "中介说房子是他们找的客户怎么办？",
      "a": "独家委托期间中介介绍的客户归中介，到期后新客户不在此限制范围内。"
    }
  ]
}
```

**设计依据**：六顶思考帽黑帽第1硬伤补充——经纪人说完之后客户会反问，当前没有字段承载"客户可能追问什么、怎么回答"。这是从"知识管理者视角"到"经纪人使用者视角"转变的关键字段。

### 6.3 `applicableRegion` — 适用地域

| 属性 | 值 |
|------|-----|
| 类型 | string |
| 填充条件 | 政策类(POL)/法规类(LAW)词条必填，其他选填 |
| 默认值 | `全国` |

```json
{
  "applicableRegion": "杭州"
}
```

**设计依据**：六顶思考帽黑帽第3硬伤——缺地域适用性字段。房产政策强地域性，杭州公积金政策不能用于北京。当前5417条中没有地域标记，是个系统性缺陷。POL/LAW类型必须标注适用地域。

### 6.4 `expiryCycle` — 有效期/更新频率

| 属性 | 值 |
|------|-----|
| 类型 | string |
| 填充条件 | 政策类(POL)必填，法规类(LAW)选填 |
| 取值 | `季度核查` / `年度核查` / `长期有效` |

```json
{
  "expiryCycle": "季度核查"
}
```

**设计依据**：六顶思考帽黑帽第2硬伤——缺时效性字段。当前有lastVerified但没有"多久该查一次"的规则。政策类每季度核查（已写入MEMORY.md规则），但数据层面没有标记。expiryCycle让巡采系统知道哪条该优先检查。

### 6.5 `useFrequency` — 使用频率标记

| 属性 | 值 |
|------|-----|
| 类型 | string |
| 填充条件 | P0词条必填 |
| 取值 | `高频` / `中频` / `低频` |

```json
{
  "useFrequency": "高频"
}
```

**设计依据**：六顶思考帽绿帽提案。标记经纪人在实际作业中碰到这个问题的频率，用于：① 推荐排序（高频优先展示） ② 生产优先级参考 ③ 小程序首页推荐。可从小豆子端的搜索/点击埋点反哺。

## 八、从经纪人视角看字段够不够

### 8.1 经纪人拿到一条词条时的典型场景

| 场景 | 需要什么字段 | 当前是否满足 |
|------|-------------|-------------|
| **客户突然问一个问题** | name→ola（一句话答出来） | ✅ 满足 |
| **客户追问细节** | detail→cp（展开说） | ✅ 满足 |
| **客户质疑"真的吗"** | legalRef→caseRef（拿出依据） | ✅ 满足 |
| **客户问"那我怎么办"** | consumerBenefit→ownerBenefit | ⚠️ 部分满足（ownerBenefit填充率3%） |
| **经纪人不知道怎么开口** | brokerScript（话术模板） | ❌ 当前散在实验字段中 |
| **客户反问/质疑** | objectionHandler（反问应对） | ❌ 不存在 |
| **客户问"杭州也是这样吗"** | applicableRegion（适用地域） | ❌ 不存在 |
| **经纪人判断该不该用这条** | caveat（注意事项）+ expiryCycle（是否过期） | ⚠️ caveat 35.7%，expiryCycle不存在 |

### 8.2 结论

- **核心层（22字段）**：覆盖了"知识是什么"的基本需求，经纪人能回答客户问题
- **缺的是"怎么用"**：brokerScript + objectionHandler 直接补上"经纪人嘴上怎么说"
- **缺的是"边界"**：applicableRegion + expiryCycle 补上"什么时候适用、是否还有效"
- **缺的是"优先级"**：useFrequency 补上"先看哪条"

**5个新字段补上后，经纪人从"知道答案"升级到"知道怎么开口、怎么应对追问、知道边界在哪"——这才是"打开就用、掏出来就有说服力"的专业工具夹。**

| 建议 | 维持8域作为基础分类 | I/J域作为"横切域"，不改变现有domain字段，通过tags新增维度标记 |

**折中方案**：不改变domain字段（避免大规模迁移），在tags中新增`skillType`维度标记：
- `skillType: "心理沟通"` → 对应I域内容
- `skillType: "市场动态"` → 对应J域内容

这样既补上了域缺口，又不破坏现有结构。
