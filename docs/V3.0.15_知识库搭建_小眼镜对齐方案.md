# 风声知识库搭建 · 小眼镜对齐方案

> 日期：2026.8.4  
> 目的：让小眼镜清楚知道「要建一个什么样的知识库、怎么分类、每条词条怎么写、分几批交付」



---

## 一、对齐目标

我们要把风声的小程序知识库从「按交易阶段堆词条」升级为「按知识域 + 业务场景 + FABE×MOT 呈现」的三层结构。

- **底层**：知识库（8 个知识域、32 个子域、每个词条含三支柱）
- **中层**：业务场景（4 条线、34 个见面场景）
- **顶层**：见面策展输出（说/带/问/跟，按 MOT 四阶段组织）

**小眼镜的角色**：负责底层知识库的词条生产、分类、填充，给引擎提供「弹药」。

**小豆子的角色**：负责把词条接入引擎、设计场景匹配规则、做产品功能。

---

## 二、一句话原则

> 每条词条都必须能回答：**这是什么事？好在哪里？对客户有什么好处？凭什么这么说？**

对应 FABE：

- **F 功能**：这是什么事（name + detail）
- **A 优势**：好在哪里（ola + cp）
- **B 利益**：对客户有什么好处（consumerBenefit）
- **E 佐证**：凭什么这么说（legalRef + dataRef + caseRef）

**数据/案例必须真实可溯源，不能编。** 找不到就写「待补充」，小豆子会诚实展示。

## 四、词条三支柱标准

每条词条最终要包含以下字段：

| 字段                | 必填 | 说明         | 示例                                 |
| ----------------- | -- | ---------- | ---------------------------------- |
| `id`              | ✅  | 唯一编码       | `P0-DELV-001`                      |
| `name`            | ✅  | 词条名称       | 换购住房退个税                            |
| `domain`          | ✅  | 所属知识域      | A3 税费法规                            |
| `subScene`        | ✅  | 适用业务场景     | 购房·议价谈判                            |
| `tags.clientType` | ✅  | 客户类型       | buyer / tenant / landlord / seller |
| `ola`             | ✅  | 一句话卖点      | 同城市卖旧买新，可退已缴个税                     |
| `cp`              | ✅  | 核心要点 3-5 条 | `["退稅条件","退稅期限","退稅金额","办理流程"]`    |
| `detail`          | ✅  | 详细说明       | 财政部税务总局公告2023年第28号...              |
| `consumerBenefit` | ✅  | 客户利益       | 节省一笔税费，降低换房成本                      |
| `legalRef`        | ⚠️ | 法规依据       | 财政部 税务总局公告2023年第28号                |
| `dataRef`         | ❌  | 数据佐证       | 2024年XX市换购退税平均金额 X 万元              |
| `caseRef`         | ❌  | 真实案例       | 客户张某，2024年3月卖旧买新，退税 X 万            |
| `source`          | ⚠️ | 来源/出处      | 财政部官网/链家研究院/内部案例                   |

**字段填写规则**：

- `legalRef`：优先找真实法规/政策原文，找不到写「待补充法源」
- `dataRef`：真实数据，注明来源和时间，找不到写「待补充数据」
- `caseRef`：真实客户案例（可匿名），找不到写「待补充案例」
- **绝对禁止编造**——宁可标「待补充」，也不能写假法源/假数据/假案例

## 五、FABE × MOT 生产模板

小眼镜生产内容时，按这个模板填：

### 5.1 FABE 四问（每条词条必填）

| FABE | 问题              | 填写示例                |
| ---- | --------------- | ------------------- |
| F    | 这是什么专业知识？       | 换购住房退还个人所得税政策       |
| A    | 相比不掌握这个知识，优势在哪？ | 帮客户合法省税，避免错过退税窗口    |
| B    | 对客户具体有什么好处？     | 同城市卖旧买新可退个税，降低换房成本  |
| E    | 凭什么相信？          | 财政部 税务总局公告2023年第28号 |

### 5.2 MOT 四阶段（场景化内容时填）

| MOT   | 阶段目标  | 小眼镜要生产的内容           |
| ----- | ----- | ------------------- |
| M1 探索 | 了解客户  | 场景引导话术、必问问题（cq）     |
| M2 提议 | 呈现方案  | 说（say）的内容，按 FABE 组织 |
| M3 行动 | 现场执行  | 带（bring）什么工具/材料     |
| M4 确认 | 共识+跟进 | 跟（followups）的下一步动作  |

## 六、与小豆子的协作流程

```
小眼镜生产词条 → 小豆子验收字段 → 小豆子同步 entries_slim.js → 引擎测试 → 场景验证
```

### 6.1 小眼镜交付物

1. **词条表格**（Excel / 飞书多维表格），每行一条，含所有字段
2. **分类标注**：每个词条必须标注 `domain`（知识域代码）+ `subScene`（适用场景）+ `clientType`
3. **来源清单**：法规/数据/案例的出处链接或文件

### 6.2 小豆子验收标准

| 验收项  | 标准                                                       |
| ---- | -------------------------------------------------------- |
| 字段完整 | name/ola/cp/detail/consumerBenefit 必填，legalRef 尽量填       |
| 分类正确 | domain + subScene + clientType 标注清晰                      |
| 无编造  | legalRef/dataRef/caseRef 找不到就写「待补充」                      |
| 去重   | 不与现有 634 条重复                                             |
| 标签规范 | 客户类型统一用 `buyer`/`tenant`/`landlord`/`seller`，不用 `renter` |

### 6.3 交付节奏

按 **知识域批次** 交付，不要按场景零散交付。比如先交完「A 法规政策域」全部词条，再交「B 金融贷款域」。

## 八、验收 checklist

小眼镜每批交付时，小豆子按这个 checklist 验收：

- [ ] 字段完整：name/ola/cp/detail/consumerBenefit 100% 填写
- [ ] 法源真实：legalRef 要么真实，要么明确写「待补充法源」
- [ ] 数据可溯：dataRef 有来源和时间，找不到写「待补充数据」
- [ ] 案例匿名：caseRef 涉及客户必须匿名处理
- [ ] 分类清晰：每条都有 domain + subScene + clientType
- [ ] 标签规范：clientType 用 buyer/tenant/landlord/seller
- [ ] 无重复：与现有 634 条和本批内无重复
- [ ] 场景匹配：能明确说出这条词条用在哪个见面场景

## 九、小眼镜开工前需要确认的 3 件事

1. **数据来源**：法规/政策从哪查？（建议：北大法宝、财政部/税务总局官网、住建部官网、各地住建委）
2. **案例脱敏**：真实客户案例能否使用？如何匿名？
3. **首批先攻哪个域**：建议首批先做 **A 法规政策域**（已有基础、最快出成果）+ **B 金融贷款域**（V3.0.13 急需）
