# 知识底座深度补充分析 — 社区服务维度与数据层重构

> 日期：2026.8.5
> 起因：生哥补充——居住服务者在社区里服务，与业主/住户/物业/居委会/商户等频繁交互，需要补充社区服务知识、社区数据等。数据字典需定义口径、指标、采集渠道、体量、为专业呈现服务。
> 方法：五轮逐层深入，从角色本质→场景拆解→知识缺口→数据层重构→实施路径

## 第一轮：角色本质——社区服务者 vs 交易撮合者

### 之前15个域的盲区

六轮分析产出的15个能力域（D1-D15），本质上是围绕**一次交易的线性流程**设计的：

```
D1获客 → D2匹配 → D3带看 → D4谈判 → D5签约 → D6资金 → D7交房 → D8运营 → D9退出
```

这是"交易撮合者"的视角——**目标是成交**。

但生哥指出，居住服务者的核心特性是**在社区里服务**：

- 他们跟社区里的**所有角色**都有频繁交互：业主、住户、物业、居委会、商户
- 他们的价值不只是"做成一单"，而是**在社区里持续创造价值、持续积累信任**
- 那个带楼盘销控表的经纪人，本质上是构建了**社区数据资产**——别人没有的信息壁垒

### 双轮驱动模型

居住服务者的工作不是一条线，而是两个轮子：

```
    交易轮（显性）                    服务轮（隐性）
    获客→匹配→带看→谈判→签约          社区扎根→信息掌握→关系维护→需求预判→服务交付
         ↓                                    ↓
    目标：成交一单                    目标：持续信任+口碑传播
         ↓                                    ↑
         └──────── 服务轮驱动交易轮 ──────────┘
```

**服务轮是引擎，交易轮是输出。** 社区服务做得越好，信任越深，交易机会自然来。

之前15个域只覆盖了交易轮，完全遗漏了服务轮。

## 第二轮：社区服务场景全景拆解

### 居住服务者在社区里到底做什么？

#### 场景1：商圈/地段信息掌握

不是泛泛知道"这个区域不错"，而是**精确到每一栋楼、每一户**：

| 信息维度 | 具体内容 | 专业呈现场景 |
|----------|---------|-------------|
| 地段价值 | 每栋楼的楼王位置、采光差异、噪音分布 | 客户问"哪栋最好"→精确到楼栋单元 |
| 交通配套 | 步行X分钟到地铁、公交站、学校、医院 | 客户问"方便吗"→精确到分钟级 |
| 商业形态 | 周边商铺类型、消费水平、人气变化 | 客户问"生活方便吗"→具体到店名和价格 |
| 规划前景 | 已批未建的项目、拆迁计划、道路改造 | 客户问"未来怎么样"→精确到规划文件 |

#### 场景2：楼盘/楼宇精细化管理（销控表思维）

生哥案例中的经纪人，核心能力是**用一张表管理每户的动态变化**：

| 数据维度 | 具体内容 | 更新频率 |
|----------|---------|---------|
| 户型面积 | 每栋楼每单元的户型分布、面积区间 | 初始建表 |
| 房屋特点 | 朝向、楼层、视野、装修状态、已知瑕疵 | 初始建表+带看更新 |
| 房屋状态 | 空置/自住/出租/在售/已售 | 月度更新 |
| 价格动态 | 挂牌价、成交价、租金水平、价格走势 | 周度更新 |
| 业主意愿 | 是否考虑出售/出租、心理价位、时间窗口 | 季度摸排 |

**这不是"知识"（教你怎么做），而是"数据"（给你具体信息）。** 属于数据层。

#### 场景3：家庭画像与需求预判

| 家庭类型 | 画像特征 | 潜在需求 |
|----------|---------|---------|
| 学龄家庭 | 有3-12岁孩子 | 学区咨询、换房到更好学区 |
| 养老家庭 | 有70+老人 | 适老化改造、换电梯房、一楼 |
| 租客家庭 | 年轻租户为主 | 换租、合租纠纷、租金谈判 |
| 宠物家庭 | 养猫/狗 | 宠物友好房源、邻里纠纷 |
| 空巢家庭 | 子女离家 | 出租空房间、换小房、养老规划 |
| 改善家庭 | 二孩/三孩 | 换大房、学区升级 |

**专业呈现**：不是问客户"您有什么需求"，而是**主动预判**——"张哥，您家小朋友明年上小学了吧？XX小学的学区政策今年有变化，我给您梳理一下。"

#### 场景4：房屋维护维修

| 服务类型 | 具体内容 | 知识需求 |
|----------|---------|---------|
| 常见问题判断 | 漏水、裂缝、管道堵塞、电路故障 | 怎么初步判断严重程度 |
| 简单维修建议 | 水龙头更换、门锁更换、下水道疏通 | 自己能修的vs必须找人的 |
| 装修指导 | 风格选择、预算估算、工期规划、避坑 | 装修流程和注意事项 |
| 维护保养 | 空调清洗、防水检查、白蚁防治 | 定期维护清单 |
| 应急处理 | 暴雨防汛、燃气泄漏、电梯故障 | 应急联络人和处理步骤 |

#### 场景5：便民服务对接

| 服务类型 | 具体内容 |
|----------|---------|
| 生活服务 | 搬家、保洁、月嫂、家教、宠物寄养 |
| 物业对接 | 缴费、报修、投诉、车位申请 |
| 政务对接 | 居住证办理、户口迁移、社区证明 |
| 商户联盟 | 周边商家优惠、合作推荐 |
| 社区活动 | 节日活动、亲子活动、老人关爱 |

#### 场景6：社区关系网络

| 关系类型 | 互动场景 | 价值 |
|----------|---------|------|
| 物业关系 | 日常对接、信息共享、互推客户 | 第一手房屋动态信息 |
| 居委会关系 | 政策传达、纠纷调解、活动参与 | 社区信任背书 |
| 业委会关系 | 议事参与、决策影响、业主联络 | 业主群体影响力 |
| 商户关系 | 资源互换、联合营销、客户共享 | 便民服务网络 |
| 邻里关系 | 日常问候、帮忙代办、信息传递 | 口碑传播节点 |

## 第三轮：知识层补充——新增D16社区服务与运营

### 为什么需要独立成域？

这些场景不能简单归入现有15个域：

- 商圈分析 ≠ D11市场洞察（市场是宏观的，商圈是微观到楼栋的）
- 楼盘管理 ≠ D2房源匹配（匹配是"找房子"，楼盘管理是"掌握每户动态"）
- 房屋维修 ≠ D8资产运营（运营是"管理资产"，维修是"服务生活"）
- 便民服务 ≠ D1获客（获客是"找客户"，便民服务是"服务社区"）
- 社区关系 ≠ D12心理沟通（心理是"理解人"，关系是"经营网络"）

**社区服务的目标是"持续信任"，不是"直接成交"。** 目标不同，知识不同，独立成域。

## 第四轮：数据层重构——从"交易数据"到"四维数据"

### 之前数据层设计的问题

六轮分析中的数据层只规划了300条，全部是**交易数据**（首付比例、税率、公积金额度）。

生哥指出：数据字典首先要定义好**数据口径、指标、采集渠道、体量**，数据是**为专业呈现服务**的。

这意味着数据层不能只回答"政策规定的数字是多少"，还要回答：
- "这个小区每户是什么情况？"（社区数据）
- "这个区域成交怎么样？"（市场数据）
- "这个学区能上什么学校？"（学区数据）

### 四维数据体系

#### A. 交易数据（已有76条→扩展至200条）

| 维度 | 内容 | 口径 | 采集渠道 | 更新频率 | 体量 |

## 第五轮：数据字典标准定义

### 数据字典条目标准模板

```json
{
  "id": "DD-COMMUNITY-001",
  "category": "社区数据",
  "subCategory": "楼盘信息",
  "itemName": "户型分布",
  
  "dataDefinition": "某楼盘各户型（一居/二居/三居/四居+）的户数及占比",
  "dataCaliber": "以开发商交付图纸为准，不含自行改造；占比=该户型户数/总户数×100%",
  "unit": "户/%",
  "valueType": "结构化数值",
  
  "dataValue": "XX小区：一居120户(15%)、二居350户(44%)、三居280户(35%)、四居50户(6%)",
  "applicableScope": "按楼盘",
  "geoScope": "杭州市西湖区XX小区",
  
  "source": "开发商交付图纸+物业核实+贝壳楼盘字典交叉验证",
  "collectionMethod": "1.物业索取户型图 2.实地踩盘核实 3.平台数据交叉验证",
  "collectionDifficulty": "中等（需物业配合）",
  "collectionCost": "低",
  
  "updateFrequency": "半年",
  "lastUpdated": "2026-08-05",
  "nextUpdate": "2027-02-05",
  
  "relatedEntries": ["词条ID1", "词条ID2"],
  "presentationScenario": "客户问小区户型时，精确说出每栋楼的户型分布和稀缺户型",
  "presentationTemplate": "{小区名}共{总户数}户，主力户型是{主力户型}（占{占比}%），{稀缺户型}只有{数量}套，比较抢手。",
  
  "reliability": 4,
  "status": "active"
}
```

### 数据口径定义规范

每个数据项必须定义：

| 字段 | 说明 | 示例 |
|------|------|------|
| dataDefinition | 数据是什么 | 户型分布 |
| dataCaliber | 怎么算的 | 以交付图纸为准，不含改造；占比=该户型/总户数 |
| unit | 单位 | 户/% |
| valueType | 值类型 | 结构化数值/文本/枚举 |
| applicableScope | 适用粒度 | 按楼盘/按楼栋/按城市 |
| geoScope | 地理范围 | 杭州市西湖区 |

### 数据采集渠道体系

| 渠道类型 | 具体渠道 | 可采集数据 | 可靠性 | 成本 | 自动化程度 |
|----------|---------|-----------|--------|------|-----------|
| 官方公开 | 房管局/教育局/央行/税务局/自然资源局 | 政策、成交数据、学区划分、土地数据 | ★★★★★ | 低 | 高（自动抓取） |
| 平台数据 | 贝壳/链家/安居客/58/自如 | 楼盘信息、成交记录、挂牌价、租金 | ★★★★ | 中 | 高（API） |
| 地图数据 | 高德/百度地图API | 配套POI、距离计算、交通规划 | ★★★★ | 低 | 高（API） |
| 实地调研 | 踩盘/物业对接/社区观察 | 户型、配套、居住氛围、房屋状态 | ★★★★ | 高 | 低（人工） |
| 社区关系 | 物业/居委会/业委会/邻居 | 家庭动态、空置率、口碑、业主意愿 | ★★★ | 低 | 低（人工） |
| 客户反馈 | 带看记录/客户回访 | 需求变化、满意度、市场感知 | ★★★ | 低 | 低（人工） |
| 数据采购 | 中指研究院/克尔达/第三方 | 市场报告、区域分析、行业数据 | ★★★★ | 高 | 中（定期采购） |

### 数据指标体系（为专业呈现服务）

数据不是存着好看的，每条数据必须回答：**客户问什么时，这个数据让经纪人显得专业？**

| 客户问题 | 需要的数据指标 | 专业呈现 |
|----------|--------------|---------|
