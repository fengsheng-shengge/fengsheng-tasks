## 一、产品总纲

### 1.1 风声定位

**AI 效率工具，辅助一线作业，帮你开单转化。**

风声不是给老板用的工具，是给**一线经纪人、给服务者**用的工具。我们解决的是：
- 「怎么帮服务者活得更好」
- 「怎么帮客户住得更美」

### 1.2 核心逻辑：双维模型

```
┌───────────────────────────────────────────────────────┐
│                    美好居住 · 双维模型                    │
├───────────────────────────────────────────────────────┤
│                                                         │
│   ┌───────────────┐         ┌───────────────┐      │
│   │   客户六维品质   │         │   服务者四维关怀  │      │
│   │                 │         │                 │      │
│   │  家庭 · 空间    │         │   能力 · 收入    │      │
│   │  决策 · 体验    │         │   尊严 · 陪伴    │      │
│   └────────┬──────┘         └────────┬──────┘      │
│            │                          │               │
│            └─────────── 双向 ──────────┘               │
│                                                         │
│      客户住得好 ←→ 服务者活得好                         │
└───────────────────────────────────────────────────────┘
```

### 1.3 一号铁律

**每个产品必须能回答两个问题：**

> 「这怎么帮客户实现美好居住？」 — 客户价值锚点
> 「这怎么帮服务者更好地活着？」 — 服务者价值锚点

**补充原则**：服务者要配得上被客户好好对待。工具不只是提升效率，更是帮助服务者成为**更专业、更有尊严、更有价值**的人。

### 1.4 用户画像

| 用户类型 | 画像 | 核心痛点 | 产品诉求 | 对应产品 |
|---------|------|---------|---------|---------|
| **C端客户** | 25-45岁，买房/租房/装修消费者 | 不知道自己要什么房；怕被坑 | 帮我明确需求；帮我选对房 | 六维品质测评 |
| **一线经纪人** | 22-40岁，房产中介，收入不稳定 | 开不了单；客户不信任；专业能力弱 | 帮我开单；帮我获客；帮我变强 | 全部付费Skill |
| **门店店东** | 30-50岁，管理5-50个经纪人 | 团队能力参差不齐；流失率高 | 团队能力评估；标准化管理 | 门店套餐 |
| **行业机构** | 培训机构/行业协会/政府 | 缺乏标准；人才评估难 | 标准认证；人才评估工具 | 机构认证包 |

### 1.5 用户旅程地图

**经纪人典型旅程（从接触到付费）：**

```
认知 → 注册 → 试用 → 付费 → 日常使用 → 续费/推荐
  ↓      ↓      ↓      ↓       ↓         ↓
 SEO   手机号  10次   首月    每日打开   包年/推荐
  ↓      ↓      ↓      ↓       ↓         ↓
埋点   埋点   埋点   埋点    埋点      埋点
```

**客户典型旅程（经纪人分享路径）：**

```
收到链接 → 完成测评 → 留资 → 经纪人跟进 → 成交
   ↓          ↓        ↓        ↓         ↓
 无需埋点   埋点     埋点     后端跟进   结果回传
```

## 三、需求管理规范

### 3.1 需求分级定义

| 级别 | 定义 | 响应时间 | 示例 |
|-----|------|---------|------|
| **P0 核心需求** | 没有就发布不了，或严重影响核心指标 | 本版本必须 | 一号铁律不通过、付费链路断裂、数据回传全断 |
| **P1 重要需求** | 有它更好，没有也能发布 | 下个版本 | 移动端适配优化、新增分享渠道 |
| **P2 优化需求** | 体验优化，不急 | 有空再做 | 文案优化、颜色调整 |

### 3.2 需求评审检查清单

每个需求评审必须回答：

- [ ] 这个需求服务哪类用户？（1.4用户画像）
- [ ] 能回答一号铁律两个问题吗？
- [ ] 需求级别是P0/P1/P2？
- [ ] 怎么衡量这个需求做成了？（指标）
- [ ] 不做会怎样？（机会成本）

### 3.3 版本规划模板

```
版本号：vX.X
```

### 4.2 时间铁律

**🔴 白天（08:00-23:59）—— 稳定运营期**

只做三件事：
1. **P0紧急修复**：页面挂了、404、功能完全不可用——立即修
2. **数据监控**：用户行为数据回收、页面健康巡检、异常告警
3. **需求规划**：写Issue、讨论方案、评审设计——不碰线上代码

**绝对禁止**：
- ❌ 白天部署新功能/重大改动
- ❌ 白天做全站替换式部署
- ❌ 白天修改路由/核心配置

**🟢 夜间（00:00-06:00）—— 迭代部署窗口**

这个时段做：
1. 新功能上线部署
2. 重大改动/重构
3. 全站更新/配置变更
4. 数据库/后端服务变更

部署前必须：
- 本地验证通过
- 小酒窝儿检核通过
- 小鱼儿终审确认
- 准备回滚方案（上一版本源码+部署记录）

### 4.3 开发流程（从需求到上线）

```
需求提出 → 需求评审 → 开发 → 自测 → 品质检核 → 终审 → 部署 → 线上验证 → 数据确认
  🐟小鱼儿    三方评审    💻小豆子   💻小豆子   🔍小酒窝儿   🐟小鱼儿   💻小豆子   💻小豆子    🐟小鱼儿
```

#### 4.3.1 需求提出

- **谁提**：生哥、小鱼儿、任何Agent
- **怎么提**：GitHub Issue，打标签（bug/feature/enhancement），标优先级（P0/P1/P2），打Agent标签
- **格式**：

```markdown
## 问题/需求
[描述]

## 预期效果
[完成后的状态]

## 验收标准
[可量化的验收条件]

## 优先级
P0/P1/P2

## 指派
@小豆子 / @小鱼儿 / @小酒窝儿
```

#### 4.3.2 需求评审（三方）

**参与**：小鱼儿 + 小豆子 + 小酒窝儿
**评什么**：
1. 这个需求**帮客户实现美好居住**了吗？
2. 这个需求**帮服务者更好活着**了吗？
3. 影响范围多大？会不会搞挂现有功能？
4. 数据回传闭环有没有？
5. 优先级对不对？

**结论**：通过→排入迭代；打回→补充信息或降级；否决→关闭Issue

#### 4.3.3 开发

- 在Issue评论"开始执行"+ 实现方案
- 关键节点在Issue更新进展
- **禁止用线上curl下载的文件覆盖部署**，必须用E盘本地源文件
- 代码必须先 `node --check` 验证语法

#### 4.3.4 自测

**测什么**：
1. 功能是否自闭环（用户能走完整个流程）
2. 现有功能是否受影响（回归测试）
3. 数据回传是否正常（tracker.js → API）
4. 页面HTTP状态码200
5. 控制台无JS报错

**自测通过→提交检核；自测不过→修到过再提交**

#### 4.3.5 品质检核（双签第一签）

**执行者**：小酒窝儿

| 检查项 | 标准 | 结果 |
|--------|------|------|
| 功能闭环 | 用户能走完完整流程 | ✅/❌ |
| 数据回传 | 行为数据能正常回收 | ✅/❌ |
| 品牌合规 | 定位语/品牌名/色值/字体符合规范 | ✅/❌ |
| 页面规范 | 导航(🏠首页+←返回)/OG标签/路径规范 | ✅/❌ |
| 安全检查 | 无明文密钥/无XSS/表单有验证 | ✅/❌ |
| 回归测试 | 原有功能未受影响 | ✅/❌ |
| 移动端适配 | 核心页面手机可正常使用 | ✅/❌ |

**全部✅ → 放行给小鱼儿终审；任一❌ → 打回小豆子修复**

#### 4.3.6 终审（双签第二签）

**执行者**：小鱼儿
**审什么**：
1. 小酒窝儿检核是否真实通过
2. 变更清单与预期效果是否一致
3. 部署时间是否合规（夜间窗口）
4. 回滚方案是否准备就绪

**终审通过→安排部署；不通过→打回并说明原因**

#### 4.3.7 部署

- 只能在**夜间窗口（00:00-06:00）**执行（P0紧急修复除外）
- 部署命令：`wrangler pages deploy . --project-name=fengsheng --branch=main`
- **全站替换需包含全部文件**，不能只部署部分
- 部署后在Issue评论部署结果

#### 4.3.8 线上验证

**执行者**：小豆子（5分钟内完成）
**验证项**：
- curl所有页面确认200
- 核心功能手动点击确认
- 控制台无报错
- 数据回传正常

**验证不过→立即回滚，明天再查原因**

#### 4.3.9 数据确认（部署后24小时内）

**执行者**：小鱼儿
**确认项**：
- 用户行为数据是否正常回收
- 新功能使用数据是否出现
- 无异常错误告警

### 4.4 P0紧急修复流程（白天允许）

**触发条件**：
- 页面完全挂掉（返回404/500）
- 核心产品功能不可用
- 数据完全丢失/泄露

**流程**：
```
发现P0 → 立即通知小鱼儿 → 小鱼儿评估影响 → 小豆子紧急修复 → 验证上线 → 事后复盘
  🐟/💻      🐟小鱼儿        🐟小鱼儿          💻小豆子         💻+🐟      🐟小鱼儿
```

**关键原则**：
1. P0修复可以白天执行，但必须**最小化变更**——只改出问题的部分
2. 修复后必须curl验证所有页面
3. 修复完成当天必须出复盘：**为什么挂的、怎么修的、怎么防下次**

### 4.5 上线底线（铁律级）

> 两条都达不到，就不上线，没有例外。

1. **功能自闭环**：用户能从入口走到终点，不卡死、不断路
2. **数据回传闭环**：用户行为数据能正常回收，不丢数据

### 4.6 变更管控

**变更前**：
- 列出**变更清单**：改了哪些文件、改了什么、为什么改
- 说明**预期效果**：改完应该变成什么样
- 确认**影响范围**：会影响哪些现有功能
- 准备**回滚方案**：上一版本源码在哪、怎么回

**变更中**：
- 增量迭代，**禁止覆盖式替换**
- 版本可溯源，每次部署有记录
- 只动必要的文件，不多改

**变更后**：
- curl全站页面验证200
- 核心功能手动确认
- 24小时内看数据是否正常

#### 5.2.1 采集字段规范

## 六、版本管理与发布规范

### 6.1 版本号规范

采用**语义化版本号**：`主版本.次版本.修订号`

- **主版本（X.y.z）**：有破坏性变更
- **次版本（x.Y.z）**：新增功能，向后兼容
- **修订号（x.y.Z）**：Bug修复

### 6.2 灰度发布规范

| 阶段 | 比例 | 观察时间 | 回滚条件 |
|-----|------|---------|---------|
| 内部灰度 | 内部团队 | 1天 | 有P0 Bug |
| 小流量灰度 | 5%用户 | 2天 | 指标下降>5% |
| 中流量灰度 | 20%用户 | 2天 | 指标下降>5% |
| 全量发布 | 100%用户 | — | 有P0 Bug |

### 6.3 回滚方案（必须遵守）

- 每次发布前必须备份（命名规则：`网站备份_vYYYYMMDD/`）
- 回滚时间要求：P0≤30分钟；P1≤2小时
- 回滚后必须做：**复盘 + 补丁 + 重新灰度**

### 6.4 GitHub为权威源

- 两个仓库：`fengsheng-website`（源码）、`fengsheng-tasks`（工单）
- 出问题以GitHub版本为准
- 线上文件≠GitHub文件 = 异常，必须对齐
