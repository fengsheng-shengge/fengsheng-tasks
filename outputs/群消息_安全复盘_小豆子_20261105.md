**一、结论**
`/api/events` 埋点接口无鉴权、字段全由客户端决定，被灌进 80 行 SQL 注入 / Log4Shell / fastjson 探针，污染了统计口径（per_product 多出 15 个假分组、per_page 多出 28 个假页面）。

但要讲清楚：**这不是 SQL 注入漏洞** —— 全仓 34 处 SQL 全部参数化，探针从未被执行，只是被当字符串存了下来。污染的是看板读数，不是数据库。

**来源判定**：两条 uid 与我方小程序 tracker 的 uid 生成格式完全一致、UA 为空、时间集中在 1~2 分钟内 → **是我方安全测试留下的痕迹，不是外部入侵**。但接口公开可写这个洞是真的，所以照样按事故处理了。

**二、根因**
SQLi / XSS 规则只挂在 URL query 上，POST body 完全没查 → 08-05 上线的 WAF 只挡住 JNDI 与 fastjson，SQLi 那批从 body 溜进去；另有一个隐藏盲区：body 检测依赖 Content-Length，chunked 请求（扫描器常用）整体绕过。

**三、今天已做完（6 个 commit，已上 main 并部署）**
1. WAF 补 body 检测（Layer 7.6）+ body 改流式限长读取，不再依赖 Content-Length
2. 写入层白名单：uid / event_type / product / page 四个维度键全部做格式校验，不合规整条丢弃（page 违规只清空 page，不误伤其它维度）
3. 清掉 80 行脏数据：events 15390 → 15310 行，全字段复扫命中 78 → 0，per_product 63 组 → 48 组、payload 组 0
4. 线上实测：三类恶意 payload 全部 403；真实小程序形态埋点正常入库（stored=1，统计同步 +1）
5. 临时审计端点已随最后一个 commit 下线（现返回 404），生产不留后门
6. 现有 6 个接口 + 首页全部 200，无回归
