**发现人**：小豆子　**发生时间**：2026-11-05 17:40 起　**状态**：根因已定位 · 已止损 · 自动恢复待验证
**代码仓库**：fengsheng-tasks / main（仓库为公开可读，这点在第二份复盘里也埋了雷）

## 一、一句话结论

**看板读数全变 0，不是数据丢了，是 D1 免费额度的「每日行读取上限」被打穿。**
真实报错（诊断端点实测）：

```
D1_ERROR: Your account has exceeded D1's free tier daily row read limit.
Upgrade to a paid plan or wait until tomorrow (midnight UTC) to continue.
```

额度 **00:00 UTC（北京时间 08:00）自动重置**。events 表数据完好（15311 行），只是读不出来。

---

## 二、为什么只有部分接口挂

D1 超限时**大部分查询直接报错**，但极少数仍能通过 —— 于是出现了一个很有迷惑性的现象：

| 接口 | 状态 | 原因 |
|---|---|---|
| `/api/stats/health` | ✅ 200 正常 | 3 条查询全部命中索引（idx_events_ts / idx_events_created_at / idx_events_event_type），读的行数很少 |
| `/api/stats/daily?days=30` | ✅ 200 正常 | 带 `created_at >=` 过滤，走索引，扫描行数少 |
| `/api/stats` | ❌ 全 0 | `COUNT(DISTINCT uid) FROM events` 无过滤条件 → 全表扫 |
| `/api/stats/summary` | ❌ 全 0 | 同上 + `GROUP BY product` 全表扫 |
| `/api/stats/pages` / `/api/stats/events` | ❌ | 同上 |
| `/api/mp-stats` | ❌ 全 0 | 内部同样是全表聚合 |
| `/api/dictionary` / `/api/knowledge-stats` | ✅ 正常 | 读的是别的表（词条表 6143 条） |

**D1 本身是通的** —— 索引命中的查询还能跑，所以「有的接口好有的接口坏」很容易被误判成代码 bug。

---

## 三、这次排查最大的障碍：错误被吞了

`handleStats` / `handleStatsSummary` 的 catch 分支只写了 `console.error`，然后落到一个**兜底分支**：

```js
return jsonResponse({ total_users: 0, ..., note: 'no database configured' });
```

也就是说：**D1 报「行读取超限」，接口对外却说「没有配置数据库」**，两者毫无关系。这个假象让我前 20 分钟一直在查「D1 绑定是不是丢了」「是不是连错库了」。

同样的问题在埋点写入侧也存在：`handleEvent` 里 `env.DB.batch()` 失败被 catch 吞掉，**仍然返回 `{ok: true}`** —— 调用方（tracker.js）以为写成功了，埋点在数据库出问题时就是这样悄悄丢掉的。

已修：两个 stats handler 与 handleEvent 的异常分支改为**回传真实 e.message**，不再伪装。

---

## 四、额度是怎么被打穿的（算账）

D1 免费额度：**每日 500 万行读取**。events 表 **1.5 万行**，而每次 stats 请求都是**全表扫**（`COUNT(DISTINCT uid)` / `GROUP BY` 没有过滤条件）。

| 来源 | 每天读多少行 | 占额度 |
|---|---|---|
| `management/index.html` 每 5 分钟轮询 `/api/stats/daily` | 288 次 × 1.5 万 ≈ **430 万** | 86% |
| 我今天的临时审计扫描（deepscan 21 次全表 LIKE + purge 21 次 + clean 约 30 次 + scan 43 次） | ≈ **200 万** | 40% |
| 日常访问 + 我反复 curl 各 stats 接口（每次 1.5 万行） | 数十万 | 数十% |

**结论**：即使没有我今天的审计扫描，`management` 页一项就占了 86% 的额度 —— **这套设计本来就随时会打穿**，今天只是被推过了线。我今天的审计扫描是压垮的最后一根稻草，这点我认。

## 五、已做的止损（今天全部上 main 并部署）

1. **统计类 GET 接口统一加缓存层**
   - `caches.default` 共享缓存（15 分钟 TTL，跨 isolate 命中）
   - isolate 内再存一份 memo，命中时**完全不碰 D1**
   - 带 `error` 的响应**不进缓存**，避免把故障缓存住
   - TTL 取 15 分钟的理由：5 分钟 TTL 最坏每 URL 每天 288 次全表扫 = 440 万行，仍会打穿；15 分钟 = 96 次/天，安全
2. **`management` 页轮询 5min → 30min**（服务端缓存之外的双保险）
3. **异常不再被伪装**：`/api/stats`、`/api/stats/summary`、`/api/events` 三处都回传真实 D1 报错
4. **顺带修掉 `management` 页的取数 bug**：原代码读 `d.total_uv` / `d.today_pv` 等字段，但 `/api/stats/daily` 返回的是 `{daily:[...]}`，而且页面上根本没有这些元素 ID → 每次都抛 TypeError，看板这 6 个数字**一直是 '--'**。改为读 `daily` 数组末项并加空值保护。
5. **临时诊断端点已下线**：诊断用的 `/api/admin/d1-diag`（令牌写在代码里）**立即移除** —— 仓库是公开可读的，令牌提交进仓库等于端点对所有人开放。这点在两份复盘里都踩到了，记下来。

线上验证：
- 缓存头生效：`X-Stats-Cache` 依次为 `MISS → MEMO → HIT → HIT`
- 写入失败现在回 `503 + 真实报错`（不再假成功）
- 恶意 payload 仍被拦（403），正常埋点写入在额度允许时正常返回 `stored=1`
