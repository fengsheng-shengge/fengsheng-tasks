## 〇、⚠️ 先看这个：光改 `clientType` 不够，还差一步（否则白改）

我做了一次**改标效果预演**（影子注入，不动真实数据），发现一个会让人白干的陷阱：

引擎的静态兜底路径只采纳 `sceneDomain ∈ {学区教育, 业主出售, 房东出租, 租住}` 四域
（见 `engine.js` 的 `_config.staticFallbackScenes`）。因此：

| 条目 | sceneDomain | 改标 clientType 后能否被采纳 |
|---|---|---|
| `P2-C1-004` / `P2-C1-015` | 学区教育 | ✅ **在兜底列表，可直接采纳** |
| `PRE-SCH-009` / `PRE-SCH-026` | 签约前 | ❌ 签约前是 API 域（在线拉取），静态路径不采纳 |
| `RENT-181` ~ `RENT-200`（20 条）| **租房** | ❌ **「租房」不在兜底列表** |

**结论：改标必须同时处理 sceneDomain，二者缺一则条目仍沉默。** 两个方案：

- **方案 A（推荐，零代码）**：改标时 `sceneDomain` 统一归 **`租住`**（或学区教育那 2 条保持 `学区教育`）→ 自动进入静态兜底路径
- **方案 B（配置改动）**：把 `租房` 加入 `staticFallbackScenes` —— 解耦后已支持 `registerDomain({ scenes: ['租房'] })`，属配置项改动，不需要改引擎逻辑，但要走一次配置变更评审

**建议给补产单的写法**：把「改标」定义为 **两件事一起做** —— ①`clientType` 追加 `tenant`；②`sceneDomain` 归到可被策展路径采纳的域。否则会出现"标签改了但页面还是不出"的假完成。

## 一、系统扫描发现的三类改标（共 44 条）

比上一版（4 条）多挖出两类，说明**标签一致性是系统性问题，不是零散个例**。

### A 类 · 租客就学（4 条，原清单不变）
内容正是租客就学、质检全达标、法源可溯，仅因 `clientType=buyer` 未进租客轴：

| id | 条目 | sceneDomain | detail | 法源 |
|---|---|---|---|---|
| `PRE-SCH-009` | 租的房子能在学区上学吗 | 签约前 ⚠️ | 237 | 租购同权实施方案；居住证暂行条例 |
| `PRE-SCH-026` | 租房能上对口学校吗和买房差在哪 | 签约前 ⚠️ | 263 | 《义务教育法》第12条 |
| `P2-C1-004` | 租房能不能上对口学区学校 | 学区教育 ✅ | 181 | 各地随迁子女入学政策及租赁入学规定 |
| `P2-C1-015` | 租房入学会占房东的学位吗 | 学区教育 ✅ | 174 | 各地随迁子女入学政策及学位使用规定 |

### B 类 · 学区教育域里的「通用/租客可共用」条目（20 条，建议整域开放）
`学区教育` 域共 60 条，**全部标 `buyer`**，但其中相当一部分语义与购房无关、租客同样关心：

| subScene | 条数 | 抽样 | 是否适合租客 |
|---|---|---|---|
| `学区政策` | 25 | `P2-C1-005` 非本地户籍孩子怎么入学 / `P2-C1-016` 入学顺位是怎么排的 / `P2-C1-017` 户口落在房子里就能上对口学校吗 / `P2-C1-018` 落户年限对入学有影响吗 | ✅ 直接适用租客 |
| `教育规划` | 15 | `P2-C3-002` 转学需要什么条件 / `P2-C3-010` 学区划分有争议怎么申诉 / `P2-C3-011` 集体户口孩子怎么入学 / `P2-C3-014` 跨区上学可以吗 / `P2-C3-015` 陪读租房怎么规划 | ✅ 直接适用租客 |
| `学校评价` | 20 | `P2-C2-002` 学校排名靠谱吗 / `P2-C2-009` 学校距离多远合适 | ✅ 租客择校/择校址同样用 |

**建议**：这 20 条**整批追加 `tenant`**（保留 buyer），成本近零、收益直接——「入学资格 + 转学 + 陪读 + 集体户 + 跨区」这一整块租客家庭决策链路就齐了，比新写 20 条快得多。

| `RENT-190` | 租房提前搬走押金能退多少 |

| `RENT-199` | 租房押金能托管吗怎么避免房东乱扣 |
| `RENT-200` | 租房怎么判断房东是否靠谱 |

**质检全部达标**：detail≥130 = 20/20、ola≥21 = 20/20、legalRef 真实可溯 = 20/20。
**但 ownerBenefit = 0/20**（这一批可与 180 条回填合并同批做）。

**为什么沉睡**：引擎的 `clientType` 加权只认 `tenant`，`renter` 不匹配 → 这 20 条在租住线上被当作"非租客内容"降权 ×0.15，几乎排不上来。而它们的 `sceneDomain=租房` 又不在静态兜底列表 → **双重失效**，等于从未被策展出过。

**处置建议**：
1. 统一标签口径：`renter` 与 `tenant` 是同义，建议 `tags.clientType` 改为 `tenant`（或至少追加 tenant）
2. `sceneDomain` 归 `租住`（否则仍不被采纳，见第〇节）
3. 改标后即可直接补强租住线 ①起步/②改善/④品质 三个节点

## 二、为什么这批改标值得优先做（成本对比）
